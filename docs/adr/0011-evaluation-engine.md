# ADR 0011: The evaluation engine and append-only results

- Status: accepted
- Date: 2026-10-18

## Context

FR-A1 to FR-A3 and FR-A7 (PRD §7.3): every applied control is checked against facts, the outcome is explainable and fresh, and a failed check is never confused with one that could not run. ADR 0010 left the engine its interface: `PolicyService.active_applied_controls`, the applied-control events, and results keyed by `(applied_control_id, rule_version_id, subject, fact snapshot)`. ARCHITECTURE §7.4 and §7.5 sketch the rest. This slice builds the engine with its first rule type, `retention_window`.

## Decisions

1. **One `evaluation` module and schema** with two tables, `evaluation_run` (trigger, who asked, start, finish, counts) and `evaluation_result`. It reads policy only through `PolicyService`, inventory through `AssetService.retention_of`, and connectors through `ConnectorsService.oldest_record_of_asset`; it keeps ids of policy's rows, never foreign keys.
2. **Evaluators are pluggable and split in two.** `gather(subject, reader, today)` reads the facts a rule needs from the modules that own them and returns plain JSON; `evaluate(facts, params)` is a pure function to a `Verdict` (outcome, measured, threshold, unit, reason). Evaluators are registered by `rule_type` in `evaluation/domain.EVALUATORS`; a rule type declared in policy without an evaluator is skipped, not failed. Adding a rule type is one entry in policy's `RULE_TYPES`, one evaluator class and, where it reads a new fact, one method on the owning module's service. Evaluators get a `FactReader`, so tests supply facts without a database.
3. **Results are append-only.** A trigger on `evaluation.evaluation_result` refuses `UPDATE` and `DELETE`, as for `policy.rule_version`; a re-evaluation writes a new row. A result stores the applied control, control code, rule type, rule version, the subject (type, id, name, domain copy for scoping), the run, `evaluated_at`, `stale_after`, `outcome`, `measured`, `threshold`, `unit`, `reason`, `facts`, `fact_hash`, `previous_result_id` and `transition` (`first`, `unchanged`, or `<before>_to_<after>`). "Latest" is the highest id (uuidv7 is time-ordered) per applied control.
4. **Idempotency compares with the latest result.** The key is the applied control, its rule version and the SHA-256 of the canonical facts. If the latest result for the applied control has the same rule version and hash, nothing is written. It is the latest, not any earlier result, that is compared, so facts that go A, B, A write three results and "latest" stays true. A Postgres advisory transaction lock per applied control keeps two workers from both writing. Because the facts include the harvest snapshot and the day measured (`as_of`), a new harvest or a new day writes a new result even when the oldest record has not moved: ages change with the calendar, and this keeps the history a daily record.
5. **`error` is an outcome, never a `fail`.** `FactsUnavailableError` (no table is mapped to the asset, the store has never been harvested, the table has no date column, the store is unreachable) becomes an `error` result with the message as its reason; any other exception is logged and recorded as a generic `error` without the internals. The facts of an error carry the day and the message, so an unchanged problem is written once a day, not once a run. Counts, filters (`outcome=fail`) and the UI treat the three outcomes apart; the UI shows `error` as "Could not evaluate" in the pending style, never in the failing colours. `not_applicable` is written when the rule's subject does not qualify (an asset that is no longer stored).
6. **Freshness.** Each evaluator declares a `freshness` (48 hours for `retention_window`); `stale_after = evaluated_at + freshness`, and the API computes `is_stale` when it reads. A schedule (`evaluation.sweep`, every `DMC_EVALUATION_INTERVAL_SECONDS`, default six hours) re-evaluates everything so results stay fresh; a stale result in the UI says so and offers Run evaluation. Reads also return the result's `evaluated_at` and `stale_after` in `meta`.
7. **Three triggers, all jobs.** All evaluation runs in the job `evaluation.run` (payload: applied control ids, trigger, who asked), so it retries with backoff.
   - *Events:* `policy.applied_control_derived` (a control now applies, or was re-derived under a new rule version: policy now publishes it for that too), `inventory.subject_changed` (say, an asset's retention policy was edited) and `connectors.harvest_succeeded` (new; evaluates the assets with a table in the store). Handlers only enqueue, with an idempotency key per event.
   - *Schedule:* `evaluation.sweep` queues `evaluation.run` in batches of 50.
   - *On demand:* `POST /evaluations` with an applied control id, or a subject type and id, returns 202 and a job. Governance, Data Owners, Data Stewards and Application Owners may run it in their domains (`run_evaluation`); the request is audited as `evaluation.requested`.
8. **Audit.** The audit trail records on-demand requests, and each result whose outcome differs from the one before it (`evaluation.result_recorded` by `system:evaluation`, with the reason). A result written with the same outcome on newer facts is not audited; the results table is the record. Every result is also published as the outbox event `evaluation.result_recorded` for actions (slice 7).
9. **`retention_window`.** Subject: a stored asset. Facts: the asset's declared retention policy (days) and the oldest value of the creation date column of the table mapped to the asset, read by `min(column)` through the store's read-only connection (same account, read-only session and statement timeout as harvest). The column is the first of `created_at`, `created`, `placed_at`, `opened_at`, `inserted_at`, `timestamp` that is a date or timestamp in the last harvest, else the first date column; a person cannot yet choose it. Verdict: the age in whole days from that record to the day measured, against `retention_days + grace_days`; over the limit fails, an empty table passes. If several tables are mapped to one asset, the first by data store and path is measured (to revisit with the mapping UI). The age is not stored on `physical_object`: it is read on demand and kept in the result's facts, so harvest still reads no rows.
10. **Reads.** `GET /evaluation-results` (latest per applied control by default; `latest_only=false` for the history; filters by applied control, control, subject, outcome) and `GET /evaluation-results/{id}`, scoped to the caller's domains. `allowed_actions` on the list offers `run_evaluation` when it is narrowed to one applied control or subject the caller may evaluate. `applied_control.latest_result_id` is not added: policy cannot import evaluation, so the UI joins the two lists.
11. **UI.** The Controls area shows each applied control's latest result beside it (replacing "Not evaluated yet"), and a row opens the evaluation: measured against the limit, the reason with `ExplainWhy` (its "Based on" list is the facts), the facts, freshness, earlier results and Run evaluation. The asset's Assess stage lists its applied controls the same way.

## Consequences

- A result always says what it was judged on, so it stays explainable after the rule or the data changes.
- The history grows by at most one row per applied control per day (plus one per change); fine at this scale. Partitioning or pruning is a later decision, and pruning would need an exception to the append-only trigger.
- Reading `min(column)` can be slow on a big unindexed table; the statement timeout turns that into an `error` result rather than a hang. Revisit if estates grow (an indexed column, or a sampled estimate).
- A rule version's change re-evaluates every applied control, with no mixed state: each result names its version.
- `harvest_fresh` and `declaration_complete` have no evaluator yet, so their applied controls read "Not evaluated yet".

## Not decided here

- Which retention policy source is authoritative when a data category and an asset disagree (ROADMAP open question); the rule uses the asset's declared policy.
- Exceptions on results (`effective_status`, slice 8), actions raised from failures (slice 7) and recurrence (slice 9).
