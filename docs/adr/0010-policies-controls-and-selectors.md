# ADR 0010: Policies, controls, versioned rules and applied controls

- Status: accepted
- Date: 2026-10-18

## Context

FR-P1 to FR-P4 and FR-A5 (PRD §7.2, §7.3): a control library under policies, applicability by attribute and never by named entity, applied controls derived and recomputed when attributes change, rules versioned so results stay explainable, and a reason for every derived item. ARCHITECTURE §6.2 and §7 sketch the model and the selector. This slice builds it; the evaluation engine (slice 6) reads it and must not need to know how it works inside.

## Decisions

1. **One `policy` module and schema** with four tables: `policy`, `control`, `rule_version` and `applied_control`. Evaluation tables stay out; `applied_control.latest_result_id` and `effective_status` arrive with slice 6.
2. **A selector is JSON with a closed vocabulary.** `{"subject": "asset", "where": {"is_stored": true, "data_category.in": ["personal", "payment"]}}`. Each key in `where` is an attribute of the subject type, optionally suffixed `.in` or `.not_in`; every condition must hold; an empty `where` selects every subject of the type. A key that is not an attribute is refused, and no attribute is a name or id, so a selector cannot name an application or an asset (FR-P2). There is no expression language: it is the smallest thing that answers FR-P2 and can be rendered as sentences ("Stored is yes; Data category is one of Payment, Personal") and edited with a form. An attribute with no value (an asset with no data category) matches `.not_in` and never matches equality or `.in`.
3. **Attributes belong to inventory, not policy.** `inventory.service.SubjectCatalog` lists the attributes per subject type (with options from reference data) and returns `SubjectFacts` (attributes, name, domain, accountable and responsible user ids). Policy never reads inventory tables. Subject types are `asset`, `data_store` and `application`. Attributes: asset `type`, `domain`, `data_category`, `is_stored`, `retention_policy`, `contains_pii`, `contains_cde`; data store `type`, `environment_type`, `domain`, `region`; application `criticality`, `hosting`, `lifecycle_status`, `domain`. Fast-changing facts (harvest status, row counts) are deliberately not attributes: they are what rules evaluate, not what selects. New attributes are added in `inventory/subjects.py`.
4. **Rule types are declared in policy** (`domain.RULE_TYPES`): key, label, the subject types it applies to and its typed params. Policy validates params and that the selector's subject suits the rule type. The evaluator for each type is slice 6's; the first three types are `retention_window`, `harvest_fresh` and `declaration_complete`.
5. **Versions are immutable and the latest is current.** A control's rule (params and selector) lives in `rule_version` rows numbered from 1. A trigger rejects `UPDATE` and `DELETE`. Publishing a version needs a reason (a looser rule is a risk decision, ADR 0006): it is stored as `change_reason` and in the audit event (`reason_required=True`). A control's name, description, owner and evidence requirement change in place, audited, without a version. The rule type is fixed for the life of a control. A control is never deleted: `retired` with a reason, after which it applies to nothing.
6. **An applied control is a row per control and subject, never deleted.** `applied_control` carries the subject (type, id, name and domain, kept current for lists and scope), `accountable_id` and `responsible_id` (asset: Data Owner and Data Steward; application and data store: Application Owner and technical owner), the `rule_version_id` it was last derived under, a stored `reason` (a sentence: "Applies because Stored is yes; Data category is one of Payment, Personal (it is Payment)") and `derived_from` (rule version and the attribute values read). A partial unique index allows one *active* row per control and subject. When the subject stops matching, the row is retired with `retired_reason` ("No longer applies: Data category is one of Payment, Personal is required but it is Operational"); matching again creates a new row, so history stays. Reads are filtered to the caller's domains by `subject_domain_id`.
7. **Derivation runs in two places that share one step.** `Derivation._sync` compares subjects with a selector and creates, refreshes or retires rows.
   - *A subject changed:* inventory publishes the outbox event `inventory.subject_changed` (`subject_type`, `subject_id`) in the transaction of every write that can change an attribute or an accountable person (asset, element, ownership assignment, application and data store writes). The worker's handler `policy.derive_applied_controls` runs `derive_subject`, so a new asset inherits its controls and an edited one gains or loses them within a worker poll.
   - *A control's rule changed:* creating a control, publishing a version and retiring one enqueue the job `policy.recompute_control` (idempotency key per control, version and status), which runs `recompute_control`. `POST /controls/{id}/recompute` queues it on demand and returns 202.
   - Both take one Postgres advisory lock, so concurrent derivations never interleave. Derivation is idempotent: running it again changes nothing.
   - Each created or retired row is audited as `system:policy` (`applied_control.derived`, `applied_control.retired`, with the reason) and published as `policy.applied_control_derived` or `policy.applied_control_retired`.
8. **The interface for the evaluation engine** is `PolicyService`: `active_applied_controls(rule_type_key=, subject_type=, subject_id=)` returns `AppliedControlRef` (applied control id, control code, rule type, the `rule_version_id` and number, params, selector, subject, accountable and responsible, reason), `find_applied_control(id)` returns one, and the three outbox events above say when the set changed (`policy.rule_version_published` carries `control_id`, `version`, `rule_version_id`). Results key on `(applied_control_id, rule_version_id, subject, fact snapshot)`. Evaluation reads policy only through `service.py` and writes its own tables.
9. **Permissions.** Everyone signed in reads policies, controls and (within their domains) applied controls. Only the governance role creates and edits policies and controls, publishes versions, retires and recomputes (`create_policy`, `edit_policy`, `create_control`, `edit`, `publish_rule_version`, `retire`, `recompute`), none scoped to a domain because the library is not.
10. **The UI** is the Controls area: Applied controls (every subject with a control, status, accountable and a "Why?" from `ExplainWhy`), the Control library with a detail panel (rule as sentences, applied subjects, version history; edit, publish a new version and retire through `ConfirmWithReason`), and Policies. The rule editor builds selectors from the API's vocabulary and shows how many subjects the selector matches before saving (`POST /controls/preview-selector`). Applied controls show "Not evaluated yet" until slice 6.

## Consequences

- Adding an attribute is one entry in inventory; adding a rule type is one entry in policy plus an evaluator.
- A new rule version is not applied instantly: the applied controls follow when the worker runs the recompute job, so the UI refetches shortly after a change.
- Derivation after a subject changes is one event per write; bulk changes produce many small events. Fine at this scale; batch by subject if it is not.
- Selectors cannot express "or" or compare two attributes. If a control needs that, add a `any_of` group rather than a language.

## Not decided here

- Periodic design review of controls (FR-P5), which needs actions (slice 7).
- Which regulations a policy cites; policies carry no regulation field until that is decided.
